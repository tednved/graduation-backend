### 迁移内容与顺序

`V6` 共 4 条 `ALTER TABLE`，按 `users` → `refresh_tokens` → `file_objects` → `orders` 执行：

| 列 | 迁移后排序规则 | 依赖它的唯一键 |
| --- | --- | --- |
| `users.openid` | `utf8mb4_0900_bin` | `uk_users_openid(openid)` |
| `users.unionid` | `utf8mb4_0900_bin` | 无 |
| `refresh_tokens.device_id` | `utf8mb4_0900_bin` | 无 |
| `file_objects.object_key` | `utf8mb4_0900_bin` | `uk_file_objects_object_key(object_key)` |
| `orders.order_no` | `utf8mb4_0900_bin` | `uk_orders_order_no(order_no)` |
| `orders.client_request_id` | `utf8mb4_0900_bin` | `uk_orders_buyer_request(buyer_id, client_request_id)` |

- **表默认排序规则不变**：15 张表仍是 `utf8mb4` / `utf8mb4_0900_ai_ci`。展示与搜索文本（`nickname`、`title`、`description`、`original_name`、`reject_reason` 等）继续大小写不敏感，本迁移**不做整表转换**。
- `MODIFY COLUMN` 未带 `FIRST`/`AFTER`，列位置不变；列上及包含它的既有索引随列排序规则一并生效，不被删除或改名。
- 自 `ai_ci` 收紧到 `bin` 是唯一性判定上的**放宽**（更少折叠），不会凭空产生重复键冲突。
- 全部 `utf8mb4_0900_*` 都是 NO PAD，`'abc'` 与 `'abc '` 始终是不同值；V6 前后尾随空格语义不变。
- 依赖 MySQL **8.0.17+**（`utf8mb4_0900_bin` 自该版本提供）。

### 缺陷来源与边界

6 列问题源于早期"整表统一排序规则"的建表规划：V1～V4 建表时未对这 6 列写列级 `COLLATE`，使其继承表默认 `utf8mb4_0900_ai_ci`。V1～V5 已执行且永久只读，因此按总纲 v2.6 §5.4 **用新增迁移修正，不回写旧迁移**；这条边界不因缺陷已被记录而放宽。

## 关键规则

- 权限：无变化；测试只用运行时注入的账号，不在仓库、日志、交接中登记凭据。
- 事务：V6 的 4 条 `ALTER TABLE` 由 Flyway 在迁移事务内执行；MySQL 8 的 DDL 为隐式提交，迁移失败时 Flyway 历史表不会记录 V6，可安全重跑。
- 状态与幂等：
  - 第二次 `migrate()` 在 V6 之后**执行 0 个迁移**（`migrationsExecuted == 0`、`pending()` 为空、`validate()` 通过），已由升级路径用例断言；
  - 幂等键：同一买家 `client_request_id` 大小写不同视为**不同**请求，完全相同仍被 `uk_orders_buyer_request` 拒绝——这是本次修复的业务目的，由 `clientRequestIdIsCaseSensitivePerBuyer` 断言。

### 用例清单

`IdentifierCollationIT`（8 个，全部在外部模式下实跑，0 skipped）：

1. `freshDatabaseMigratesThroughV6AndKeepsFifteenTables` — 空库执行 V1～V6 共 6 个迁移，15 张业务表齐全，版本顺序 1..6。
2. `onlyExactIdentifierColumnsUseBinaryCollation` — 遍历 `information_schema.columns`：6 个标识符列均为 `utf8mb4_0900_bin`，**其余每个文本列**仍为 `utf8mb4_0900_ai_ci`（证明没有整表转换）。
3. `openidIsCaseSensitiveAndStillUnique` — `oAbC…` 与 `OaBc…` 可同时存在并各自读回原值；完全相同的 openid 仍触发 `uk_users_openid` 冲突。
4. `objectKeyDeviceIdAndOrderNoAreCaseSensitive` — 三个列的大小写变体可共存，等值查询不再折叠（`WHERE object_key = ?` 只命中同大小写行）。
5. `clientRequestIdIsCaseSensitivePerBuyer` — 同一买家不同大小写的 `client_request_id` 是两条不同订单；完全相同仍被 `uk_orders_buyer_request` 拒绝。
6. `trailingSpacesAreSignificantAndValuesAreNotNormalized` — 尾随空格参与比较（NO PAD），写入后读回不做 trim、不改写大小写。
7. `displayTextKeepsTableDefaultCaseInsensitiveCollation` — 展示文本（如 `nickname`）仍大小写不敏感。
8. `v5ToV6UpgradePreservesDataDefinitionAndChecksums` — `target("5")` 先断言 V5 基线（含 6 列此时仍是 `ai_ci`）→ 插入样本 → 升级 V6 → 断言列排序规则、标识符原值、行数、15 张表、列定义指纹、索引、27 个外键、V1～V5 校验和全部不变 → 第二次迁移 0 个、`pending()` 为空、`validate()` 通过。

`FlywayMigrationIT` 的相应改动：`executesSixMigrationsOnEmptyDatabase`（6 个迁移）、`recordsVersionsOneToSixInOrder`（1..6）、新增 `v1ToV5BaselineStillHoldsUnderTargetFive`（`target("5")` 下 5 个迁移、15 张表、`MAIN` 校区、5+7 分类、`openid` 仍为 `ai_ci`）——DB-01 原有的迁移约束用例逐条保留，未删除。

### 测试用临时 schema 与清理

测试夹具自建一次性 schema，**不对锚点 schema 执行任何 DDL/DML**，也不调用 Flyway `clean()`、不做 `DROP`：

- `db02_it_fresh_<随机后缀>`：空库路径；
- `db02_it_v5baseline_<随机后缀>`：`target("5")` 基线；
- `db02_it_upgrade_<随机后缀>`：`target("5")` → 升级 V6。

这些 schema 有意不自动删除（避免测试里出现破坏性 DDL）。复核后可手工清理：

```sql
SELECT schema_name FROM information_schema.schemata WHERE schema_name LIKE 'db02%';
DROP DATABASE IF EXISTS `db02_it_fresh_<后缀>`;
DROP DATABASE IF EXISTS `db02_it_v5baseline_<后缀>`;
DROP DATABASE IF EXISTS `db02_it_upgrade_<后缀>`;
-- 锚点库保留为空库，供下次实跑：
DROP DATABASE IF EXISTS `db02_anchor`;
CREATE DATABASE `db02_anchor` CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**再次实跑前必须重建空的 `db02_anchor`**：外部模式直接在锚点库里执行 V1～V6，库中已有 V6 时 `executeSixMigrations` 会因 `migrationsExecuted == 0` 失败。

## 风险与阻塞

- 已知风险：
  1. `utf8mb4_0900_bin` 需要 MySQL 8.0.17+；已在 8.0.46 实测。若目标环境低于该版本，V6 会失败——这是任务包明确接受的前提。
  2. 由 `ai_ci` 改为 `bin` 后，**应用层**的等值查询与唯一键判定都变为区分大小写。若后续模块（BE-04 登录、BE-08 下单幂等）误把 openid / client_request_id 做大小写归一化后再入库或比对，会与数据库语义不一致。已写入交接的"下一任务输入"。
  3. 历史数据兼容性：若某环境中已存在仅大小写不同的重复标识符（`ai_ci` 下不可能同时存在，故实际不会发生），V6 也不会因此失败——收紧到 `bin` 只会放宽唯一性。**因此不需要数据清洗步骤。**
  4. 测试用的 `db02_it_*` schema 不自动清理，需人工按上节命令回收。
- 阻塞事项：无。
- 需要负责人决定：无（V6 编号可用，未与既有迁移冲突）。

## 下一任务输入

- 可直接使用的类或接口：无新增 Java 类。测试夹具位于 `src/test/java/com/graduation/backend/database/`。
- 数据库/OpenAPI 版本：**Flyway 基线 V6**（15 张业务表 + 6 个 `utf8mb4_0900_bin` 标识符列）。OpenAPI 未改动。API-01 / BE-03 / BE-04 应以 V6 为输入。
- 接入注意事项：
  1. **实体映射**：`users.openid`、`users.unionid`、`refresh_tokens.device_id`、`file_objects.object_key`、`orders.order_no`、`orders.client_request_id` 在 JPA 侧保持普通 `String` 映射即可；排序列可通过 `@Column(columnDefinition = ...)` 或 `@Collate`（Hibernate 6.5+）声明，但**须用 `spring.jpa.hibernate.ddl-auto=validate` 复核**，不要为了"让校验通过"去修改已执行的 V1～V5 迁移。
  2. **不做归一化**：外部标识符（openid、unionid、device_id、object_key、order_no、client_request_id）在应用层**不得** `trim()` 或 `toLowerCase()` 后再入库或比对；写读往返必须保持原字符与大小写，尾随空格也是有效字符。查询这些列时使用精确等值，不做 `LOWER()` 包裹（会使索引失效并绕过 `bin` 语义）。
  3. **幂等语义**：`uk_orders_buyer_request(buyer_id, client_request_id)` 现在区分大小写——同一买家用不同大小写的 request_id 会创建两条订单，这是预期行为；客户端应保证 request_id 稳定不变地重放。
  4. **展示文本不受影响**：`nickname`、`title`、`description` 等的模糊搜索继续走 `utf8mb4_0900_ai_ci`，大小写不敏感的行为没有改变。
  5. **不要新增列级 `COLLATE` 到其余文本列**：本迁移刻意只覆盖 6 个不透明标识符列，扩大范围需要新任务。
